# 软件实现

> 我现在有手机上安装一个记账软件，但是这个软件的数据是保存在其他企业上的，我认为不是很安全，我想找一个开源项目，一方面现在的AIagent特别的多，相比于软件，我认为自创一个运行在本地的记账软件更好，还可以方便我自己统计数据，因为这个软件的数据统计可能都是收费的，不方便。其次有时候我懒得记账，会在一星期的时候统一记账，这个时候如果可以通过语音的方式，快速的分类，日期等可以达到更好的效果，节省我的操作时间。最后，由于之前对于分组的不合理，导致很多账目的类型分散，不好看，并且我自己一个一个改浪费时间。如果可以本地配置一个，方便统计，并且数据本地保存，设置相应的密码，似乎更方便以及安全。数据也可以设置一个只有本机或者特殊方法可以解开的密码，之后我就可以将数据通过坚果云进行同步，也可以实现换电脑的时候的数据迁移。分析我的思路，给出建议。

我认为你的思路非常值得做，而且它不只是一个简单的「自己开发记账软件」项目。

你真正想解决的是一个更大的问题：

**建立一个属于自己的、数据完全可控、能够通过自然语言交互、可以自由分析和迁移的个人财务数据系统。**

我尤其认同你提出的几个出发点：

1. **数据主权**：财务数据不应该被某个商业软件锁定，也不应该因为更换软件而丢失。
2. **本地优先**：数据保存在自己的设备上，云端只承担加密备份和同步的角色。
3. **AI 降低记账成本**：不再要求自己每天打开软件、选择分类、输入金额，而是通过语音或自然语言完成记录。
4. **数据结构可以持续优化**：分类体系不合理时，可以批量迁移、归类和重新统计，而不是被原有软件的设计限制。
5. **数据可迁移、可分析**：随时导出原始数据，自己写 SQL、Python 或接入 AI 分析，不依赖收费的统计功能。

不过，我有一个重要建议：

**不要把项目定位成「AI Agent 记账软件」，而应该定位成「Local-first Personal Finance System（本地优先的个人财务系统）」。**

AI 是交互入口，数据库才是核心资产。即使未来 AI 模型发生变化，你的记账、查询、统计、备份和迁移也应该完全不受影响。

下面我从现有开源项目、系统架构、AI 交互、安全设计和实施顺序几个方面分析。

### 1. 数据库应该如何设计？

我建议直接使用 SQLite。

理由很简单：

- 不需要安装独立数据库服务器。
- 数据就是一个文件，便于备份。
- 支持复杂 SQL 查询。
- Python 可以直接读取。
- 可以通过加密扩展保护数据。
- 桌面端和移动端都有成熟的使用方案。

数据库至少应该有以下几张表：

| 数据表 | 用途 |
|---|---|
| accounts | 现金、银行卡、信用卡等账户 |
| transactions | 收入、支出、转账 |
| categories | 主分类和子分类 |
| tags | 旅游、工作、家庭等标签 |
| merchants | 商家及商家别名 |
| category_rules | 自动分类规则 |
| audit_logs | 修改记录和操作历史 |

交易表尤其需要设计好。

例如：

```json
{
  "occurred_on": "2026-11-16",
  "amount_minor": 3500,
  "currency": "CNY",
  "type": "expense",
  "account": "支付宝",
  "category": "餐饮/午餐",
  "merchant": "某餐厅",
  "note": "工作日午餐",
  "source": "voice"
}
```

这里有两个细节：

- `amount_minor` 使用整数表示金额的最小单位，例如 3500 表示 35.00 元，避免浮点数误差。
- `occurred_on` 和 `created_at` 应该分开。前者表示实际消费日期，后者表示录入日期。

这样你一星期后补录账目，也不会影响历史统计。

## 三、语音记账：这是最值得投入的功能

我认为你提出的语音记账，比简单地增加一个 AI 对话框有价值多了。

你真正需要的是一个批量记账助手。

### 1. 推荐的交互方式

假设你一个星期没有记账。

打开手机，点击录音，然后说：

> 上周一早上吃早餐花了 12 块，中午吃饭 35 块，晚上打车花了 28 块。周二去超市买菜花了 86 块，周三买咖啡 22 块，周五发工资到账 8500 块。

系统自动处理成：

| 日期 | 类型 | 金额 | 分类 | 状态 |
|---|---|---:|---|---|
| 上周一 | 支出 | ¥12 | 早餐 | <badge color="success">已识别</badge> |
| 上周一 | 支出 | ¥35 | 午餐 | <badge color="success">已识别</badge> |
| 上周一 | 支出 | ¥28 | 交通 | <badge color="success">已识别</badge> |
| 上周二 | 支出 | ¥86 | 买菜 | <badge color="success">已识别</badge> |

用户只需要检查一下日期、分类和金额，点击确认即可批量入账。

### 3. AI 分类应该怎么实现？

这里我建议采用混合模式，而不是全部交给大模型。

<box border radius="lg" padding={3} gap={2}>
  **第一层：规则分类**

  例如：
  - 星巴克 → 餐饮 / 咖啡
  - 地铁 → 交通 / 公共交通
  - 超市 → 生活 / 日用品

  <divider color="subtle"/>
  **第二层：AI 智能分类**

  如果规则无法识别，再让本地 LLM 根据交易描述、商家名称和历史习惯给出分类建议。

  <divider color="subtle"/>

  AI 只生成待确认记录，用户确认后才写入数据库。

1. 高频商家不需要每次调用大模型。
2. 分类结果可以逐渐学习你的习惯。
3. 即使大模型判断错误，也不会直接污染数据库。

如果希望完全本地，可以考虑在自己的电脑上运行 Ollama 或 llama.cpp，再使用适合中文结构化提取的小模型。

手机负责语音采集和离线转写，电脑负责复杂的本地 AI 解析，也可以通过局域网连接。

## 四、你提出的分类混乱问题，其实应该重点解决

我觉得这个需求甚至比语音记账更重要。

因为记账的最终价值不是记录了多少笔交易，而是这些交易能不能形成有意义的数据。

### 1. 不建议无限增加分类

例如，你现在可能存在这样的情况：

- 吃饭
- 早餐
- 午餐
- 晚餐
- 外卖
- 饮料
- 咖啡
- 零食
- 聚餐

如果这些分类全部平级，统计时就会很麻烦。

我建议采用两级分类：

    - 午餐
    - 晚餐
    - 咖啡饮品
    - 零食
    - 聚餐
  </box>
  <divider color="subtle"/>
  **交通**
  <box padding={{left:3}} gap={1}>
    - 公共交通
    - 打车
    - 加油
    - 停车
  </box>

  <box padding={{left:3}} gap={1}>
    - 日用品
    - 家居
    - 个人护理

更进一步，我建议把分类和标签分开。

例如：

一笔交易：

- 分类：餐饮 / 午餐
- 标签：工作日、公司附近、报销

这样你既可以统计餐饮支出，也可以统计工作相关消费。

### 2. 设计一个批量分类整理工具

这是我非常建议你自行开发的功能。

比如你导入原有软件的数据后，系统发现：

| 原分类 | 笔数 | 建议新分类 |
|---|---:|---|
| 外卖 | 120 | 餐饮 / 午餐 |
| 饮品 | 45 | 餐饮 / 咖啡饮品 |
| 早餐 | 36 | 餐饮 / 早餐 |
| 日常购物 | 78 | 生活 / 日用品 |
| 生活用品 | 43 | 生活 / 日用品 |

系统可以自动生成分类映射。

你只需要：

1. 检查 AI 的映射建议。
2. 查看每个分类对应的原始账目。
3. 确认批量修改。
4. 保留修改记录，支持撤销。

还可以加入商家名称归一化。

例如：

- 星巴克上海某某店
- Starbucks
- 星巴克咖啡
- 星巴克 XX 门店

这些商家可以统一归类到同一个商家。

这样未来再记账时，系统也能自动识别。

**这部分最好做成一个独立的分类管理模块，而不是简单地让 AI 修改数据库。**

## 五、数据安全与坚果云同步：这里需要特别谨慎

这是整个项目中我认为最需要认真设计的部分。

你的想法是：

本地数据库 + 密码保护 + 坚果云同步 + 换电脑恢复。

这个方向是正确的，但要注意三个层次。

### 1. App 密码不等于数据加密

例如：

你给记账软件设置一个六位密码。

它可能只是让你进入软件前输入密码，但数据库仍然是普通 SQLite 文件。

只要有人拿到数据库文件，就可能直接读取你的财务数据。

因此，我建议至少有两层保护：

| 保护层 | 作用 |
|---|---|
| App 密码 / 生物识别 | 防止别人直接打开软件 |
| 数据库加密 | 防止别人绕过软件直接读取文件 |

技术上可以考虑：

- SQLite + SQLCipher。
- AES-256-GCM 或 XChaCha20-Poly1305。
- Argon2id 密码派生。
- Android Keystore / Windows Credential Manager / macOS Keychain。

不要自己设计加密算法，直接使用经过广泛使用和审查的加密库。

### 3. 坚果云到底应该怎么同步？

我不建议直接把正在运行的 SQLite 数据库放进坚果云同步文件夹。

原因是：

SQLite 在运行时可能存在 WAL、SHM 等辅助文件。数据库文件正在写入时，如果云同步客户端恰好同步了不同时间点的文件，就可能出现数据不一致。

## 一、电脑连续开机 600 天，会有什么影响？

600 天相当于 14,400 小时。对于服务器来说，这并不算特别夸张；对于普通家用电脑，也不是不可接受的运行时间。

不同硬件受到的影响不一样。

| 硬件 | 长期运行的影响 | 主要注意事项 |
|---|---|---|
| CPU | 通常较小 | 温度、持续负载 |
| GPU | 通常较小 | 高负载和散热 |
| 内存 | 通常很小 | 稳定性 |
| SSD | 通常较小 | 写入量、温度 |
| 机械硬盘 HDD | 有持续运转磨损 | 运行小时数、温度 |
| 电源 PSU | 有一定影响 | 温度、电容老化 |
| 散热风扇 | 有持续磨损 | 轴承、灰尘 |
| 笔记本电池 | 可能比较明显 | 长期满电、温度 |

这里有几个容易被忽略的地方。

**1. 温度比开机时间更重要**

如果电脑长期处于低负载状态，CPU 温度比较低，风扇转速也不高，那么持续运行 600 天不一定会造成明显的额外损耗。

相反，如果电脑一直处于高温环境，即使每天只开机几个小时，也可能加速硬件老化。

**2. SSD 不会因为开机时间长就直接损耗大量寿命**

SSD 的寿命主要与 NAND 闪存写入量有关，而不是简单地按照开机小时数计算。

所以，如果你只是让电脑运行一个记账数据库、偶尔运行本地 AI 模型，通常不需要太担心 SSD 寿命。

**3. 风扇和机械硬盘更值得关注**

这两个部件存在比较明确的机械磨损。

如果电脑已经连续运行 600 天，我建议检查一下：

- 风扇是否出现异常噪声。
- 机箱内部是否积灰。
- CPU、GPU 是否存在异常高温。
- SSD、HDD 的 SMART 健康状态。
- 电源是否出现异响或者不稳定。

**4. 不需要为了硬件寿命每天关机**

很多人认为电脑需要每天关机休息，其实没有这个必要。

频繁开关机也会带来温度变化和电气冲击。对于运行稳定、散热良好的电脑，持续运行完全可以接受。

当然，操作系统更新、安全补丁和必要的维护重启仍然很重要。

## 一、先明确第一版究竟要解决什么问题

结合你之前的想法，我认为第一版应该围绕五个核心目标展开。

|---|---|
| 数据自主 | 所有财务数据保存在本地，不依赖第三方服务器 |

| 统计自由 | 可以自由查询、筛选、分析历史账目 |

这里有一个重要原则：

**第一版不需要 AI，但必须从数据结构上为未来的 AI 留好接口。**

例如，未来 AI 想要帮你整理过去一年的餐饮支出，只需要读取数据库并调用已有的分类管理功能，而不需要重新设计整个软件。

原有分类：

- 早餐
- 午餐
- 晚餐
- 外卖
- 饮料
- 咖啡
- 聚餐

调整为：

- 餐饮
  - 早餐
  - 午餐
  - 晚餐
  - 外卖
  - 咖啡饮品
  - 聚餐

软件应该能够将原有账目批量迁移到新分类，并在执行前显示影响的账目数量，执行后支持撤销。

这样未来即使调整十次分类，也不会破坏历史数据。

> 软件实体直接找一个开源的，之后在开源代码上进行魔改，先推荐比较好的开源项目。

我赞同这个方向，而且我认为这比从零开发更合理。

这次我们调整一下思路：**不再自己设计一套完整的记账软件，而是寻找一款已经成熟、架构合理、代码质量较好的开源记账软件，直接 Fork，然后围绕你的需求进行二次开发。**

这样可以省去大量基础开发工作，把精力集中在真正有价值的功能上：

1. 本地数据存储和隐私保护。
2. 更符合个人习惯的分类体系。
3. 高效的账目管理和批量分类调整。
4. 更自由的数据统计和可视化。
5. 后续扩展语音记账、AI Agent 和坚果云同步。

我会把**项目成熟度、代码可修改性、数据自主权、界面体验、扩展能力**作为主要筛选标准，而不只是看 GitHub Star 数量。

### 这里最重要的是数据流

假设你对 Workbuddy 说：

> 昨天中午在麦当劳吃饭花了 38 元，帮我记一下。

工作过程应该是：

1. Workbuddy 解析出金额、日期、商家和分类。
2. 调用本地接口 `create_transaction`。
3. 本地程序校验参数、写入数据库。
4. 返回记账成功的信息。

再比如：

> 帮我分析今年餐饮支出最多的月份，以及同比变化。

工作过程应该是：

1. Workbuddy 调用 `run_analysis`。
2. 本地 Python 程序读取解密后的数据库。
3. Python 使用 SQL / Pandas 完成计算。
4. 只返回计算结果、必要的统计摘要。
5. Workbuddy 根据结果组织语言。

**关键是：不向 Workbuddy 的大模型发送原始账单、完整交易列表或数据库文件。**

例如，本地 Python 返回：

```json
{
  "period": "2026",
  "category": "餐饮",
  "total": 12680.50,
  "highest_month": "2026-06",
  "highest_month_total": 1580.00,
  "year_over_year_change": 0.12
}
```

Workbuddy 只需要解释这个结果即可。

这也意味着，未来你可以编写自己的 Python 分析脚本，甚至不需要修改记账软件本身。

## 三、我的最终选型建议

如果把这些项目放在一起，我会这样判断：

| 项目 | 最大优势 | 主要缺口 |
|---|---|---|
| Bastide | Python 后端、桌面界面、本地 API | 需要加密和 MCP |
| Fungible | GUI、MCP、REST API 已有 | 完整数据库加密、记账新增接口 |
| MoneyBin | Python、加密数据库、MCP | 缺少桌面 GUI |
| MMEX | 成熟、分类丰富、AES 加密 | 加密数据库难以直接被外部程序访问 |
| Open Finance | Agent 权限管理和财务界面 | 数据库加密范围需要核实 |

这里我需要修正一下前面关于 Open Finance 的判断：它的 README 声称使用 AES-256-GCM 静态加密，但开发者架构文档具体描述的是 Plaid 凭据和访问令牌加密，底层使用 `better-sqlite3`。因此，我目前不能确认整个 SQLite 文件都已加密，不应该直接把它视为满足你的整库加密要求。([github.com](https://github.com/DeseretSaint/open-finance/blob/main/docs/PLAN.md), [github.com](https://github.com/DeseretSaint/open-finance/blob/main/README.md))

另外，MMEX 的官方文档明确说明，`.emb` 加密数据库无法通过普通外部 SQLite 工具直接访问。这会给 Python 分析增加不少工作。([moneymanagerex.org](https://moneymanagerex.org/moneymanagerex/en_US/index.html))

### 我的选择

我更倾向于：

**以 Bastide 为基础，借鉴 MoneyBin 的加密和 Agent 接入设计。**

原因很简单：

- Bastide 已经有桌面软件。
- 后端是 Python，不需要额外维护一套复杂的分析服务。
- FastAPI 已经提供本地接口。

- Workbuddy 可以通过 HTTP API 或 MCP 访问。

MoneyBin 则值得研究它如何实现 AES-256-GCM 整库加密、密钥管理和 MCP。它目前是预发布阶段，没有完整桌面 GUI，Windows 支持也尚未验证，因此我更愿意把它当作技术参考。([github.com](https://github.com/bsaffel/moneybin), [github.com](https://github.com/bsaffel/moneybin/blob/main/docs/guides/database-security.md))

### 关于数据库和接口，我建议特别注意两点

**第一，Python 分析和 Agent 记账使用同一个数据库。**

不需要维护两份数据，也不需要在两个软件之间同步。

Python 可以通过 SQLAlchemy 使用 SQLCipher 兼容的数据库驱动，所有查询都在本机完成。

**第二，不要允许 Workbuddy 随意执行 Python 代码或任意 SQL。**

更好的做法是预先提供一些功能：

```text
create_transaction()
query_transactions()
update_transaction()
list_categories()
bulk_update_category()
run_analysis()
```

例如：

```python
def run_analysis(report, start_date, end_date):
    if report == "monthly_expense":
        return analyze_monthly_expense(
            start_date,
            end_date
        )

    if report == "category_ranking":
        return analyze_category_ranking(
            start_date,
            end_date
        )
```

这样 Workbuddy 只能调用你允许的分析功能。

数据库查询使用只读连接，写入经过业务逻辑校验，批量修改可以保留撤销记录。

## 五、微信和支付宝自动记账

这个功能我认为非常值得保留，但不用第一版就实现实时自动同步。

实际上，可以先做一个很实用的方案。

<box border radius="lg" padding={3} gap={2}>
  <row align=center gap={2}>
    [图片：Alipay app logo icon]
    **支付宝账单**
  </row>
  官方提供电脑端账单查询和下载功能，可以将下载的文件交给本地导入程序处理。([cschannel.alipay.com](https://cschannel.alipay.com/mobile/helpDetail.htm?help_id=201603346502), [cschannel.alipay.com](https://cschannel.alipay.com/mobile/helpDetail.htm?help_id=201602030903))
  <divider color="subtle"/>
  <row align=center gap={2}>
    [图片：WeChat Pay green logo icon]
    **微信支付账单**
  </row>
  官方隐私说明提供了从微信钱包账单入口下载交易记录的方式。([pay.wechatpay.cn](https://pay.wechatpay.cn/xdc/weardeviceagreementweb/html/agreement/tenpay_user_privacy))
</box>

软件增加一个导入功能：

1. 选择微信或支付宝账单。
2. Python 自动解析文件。
3. 根据交易流水号检查重复记录。
4. 根据商家、商品描述、原始交易类型匹配分类。
5. 无法确定的记录进入待确认列表。
6. 确认后写入数据库。

例如：

| 商家 | 原始描述 | 自动分类 |
|---|---|---|
| 星巴克 | 咖啡消费 | 餐饮 / 咖啡 |
| 美团 | 外卖订单 | 餐饮 / 外卖 |
| 滴滴 | 出行订单 | 交通 / 打车 |
| 京东 | 商品订单 | 购物 / 日用品 |

随着你不断修正分类，系统会积累规则。

至于付款后实时自动记账，目前我查到的微信和支付宝官方个人用户流程主要是账单下载，而不是面向个人第三方软件的通用实时交易推送接口。因此，先做好可靠的文件导入，后续再研究通知捕获或其他可用的授权接口，会更实际。

**Workbuddy 智能体究竟在哪里运行？**

如果 Workbuddy 在本机运行，我们甚至可以不开放任何公网端口，使用本地 MCP 或 `127.0.0.1` 接口即可。

如果它在云端，就需要额外解决安全访问本地 API 的问题，不能简单地把数据库服务暴露到公网。

**我现在的目标是：尽量利用现有开源软件，只修改真正需要的部分，最终得到一个安装在电脑上、可以独立使用、可以被 Workbuddy 操作的个人记账软件。**

不做商业化设计，不提前考虑不需要的功能。先把这个小工具做得顺手、可靠就好。😊
